1.2 Principles

IDPrincipleApplication
DM-01Scope columns are mandatoryEvery operational table carries gym_id and location_id, both NOT NULL. These are not conveniences — they are the columns RLS policies filter on, so a table missing them cannot be isolated.
DM-02Invariants live in constraintsIf a rule can be a CHECK, a UNIQUE, a partial unique index or a foreign key, it is one. Application code can be bypassed by the next code path; the database cannot.
DM-03Money is never floating pointbigint minor units plus an explicit currency column. No float, no double, no real anywhere near an amount.
DM-04Financial and factual history is append-onlyPayments, attendance, credit movements and audit entries are never updated or deleted. Corrections are new rows referencing the original.
DM-05Ledger plus balance, not balance aloneWhere a running total exists (PT credits, class packs), an immutable transaction ledger is the truth and the balance column is a locked, constrained cache of it. The ledger explains how a balance got there.
DM-06Soft delete for anything referenceddeleted_at timestamptz on entities that history points at. A hard DELETE of a member orphans their attendance and payments.
DM-07Time is UTC, stored with zonetimestamptz throughout, rendered in the tenant's timezone at the edge. A timestamp without zone is a future bug in a multi-timezone product.
DM-08Enums are Postgres typesNot free strings, not integer codes. Adding a value is a migration, which is correct — a new booking state should be a deliberate decision, not a typo someone inserted.
DM-09JSONB only for genuinely variable shapesHealth screening answers, AI payloads, audit before/after, notification template variables. Never for data that is queried, joined or constrained.
DM-10No triggers, no stored proceduresBusiness logic lives in the application where it is testable and reviewable. Constraints are declarations, not logic, and are the one exception.

2.1 The three spine relationships

Almost everything in the schema hangs off three relationships. Getting these right is most of the design.

RelationshipCard.Why it is shaped this way
gyms → locations1 : NA gym runs many locations. Every operational row carries both ids, not just location_id, even though location implies gym. The denormalisation is deliberate: RLS filters on gym_id first and a join to resolve it on every query would be ruinous.
users → role_grants1 : NAuthority is a set of grants, never a column on the user. This is what allows Trainer + Location Admin simultaneously (FR-AUTH-26) and scoping per location (FR-AUTH-28). A role column on users could express neither.
users → fitness_profiles1 : 1Every account, whatever its role. Created with the user, never granted, never revoked (FR-PFP-01). This single relationship is what makes the dual-facet model real rather than aspirational.
The one relationship that does not exist, deliberately. There is no members table and no member_id anywhere. A member is a user holding a MEMBER role grant — nothing more. Had "member" been its own entity, staff could not train without a second account, and every training table would need a nullable second owner column. Modelling membership as a grant rather than an identity is what makes FR-PFP-01 fall out naturally instead of needing special cases throughout.

Constraints that encode a requirement

-- FR-SUB-04: a gym has at most one live subscription at any time
CREATE UNIQUE INDEX uq_gym_subscriptions_live
    ON gym_subscriptions (gym_id) WHERE state = 'LIVE';

-- §13: the public URL is /gyms/{gym-slug}/{location-slug}, so location slugs
-- need only be unique within their gym, and gym slugs globally.
CREATE UNIQUE INDEX uq_locations_gym_slug ON locations (gym_id, slug);

-- Geofence radius must be sane: a 5km radius defeats the point (FR-ATT-02)
ALTER TABLE locations ADD CONSTRAINT ck_locations_radius
    CHECK (checkin_radius_m BETWEEN 20 AND 500);

geography(Point,4326) requires the PostGIS extension. It earns its place twice over: geofenced check-in needs an accurate distance calculation, and the public location pages need "gyms near me" ordering (§13). Computing great-circle distance in application code over a growing table would be both slower and wrong at the edges.

Why a junction table rather than a location_ids uuid[] column. LB-ARCH-1.0 §5.2 sketched the scope as an array. A junction table is the better model and supersedes that sketch: an array cannot have a foreign key, so it will eventually hold the id of a deleted location with nothing to stop it; "which admins cover location X" is an indexed join rather than a full scan of an array column; and RESTRICT on the location FK prevents closing a location out from under its administrators. The RLS context still needs a fast list, so the session filter builds the location CSV once per request from this table — one indexed query, not a per-row join. Recorded in Appendix A.

Constraints

-- FR-AUTH-11: one live grant of a given role per user per gym.
-- Partial unique index, not a UNIQUE constraint: revoked grants stay as history
-- and must not block a later re-grant of the same role.
CREATE UNIQUE INDEX uq_role_grants_live
    ON role_grants (user_id, gym_id, role) WHERE revoked_at IS NULL;

-- FR-AUTH-18: only GYM_OWNER and SUPER_ADMIN may hold gym-wide scope.
ALTER TABLE role_grants ADD CONSTRAINT ck_role_grants_gym_wide_role
    CHECK (NOT is_gym_wide OR role IN ('GYM_OWNER','SUPER_ADMIN'));

-- FR-AUTH-22: last-admin protection. A partial unique index cannot express
-- "at least one", so this is enforced in the service layer under a lock on the
-- gym row — one of the few invariants the database genuinely cannot hold.
Where DM-02 does not reach. Last-admin protection is a minimum cardinality rule, and SQL constraints can only express maxima and shapes. It therefore lives in IdentityService, guarded by a row lock on the gym, with a dedicated concurrency test proving two simultaneous demotions cannot both succeed. Naming the exception matters: an invariant everyone assumes the database is holding, which it is not, is exactly how these fail.

Gapless receipt numbering, and why a Postgres SEQUENCE will not do. GST requires invoice numbers to be consecutive with no gaps. A SEQUENCE is explicitly non-transactional — it does not roll back — so an aborted transaction permanently burns a number and leaves a hole. The receipt_sequences table exists solely to provide a number that is transactional: increment it under a row lock in the same transaction as the receipt insert, and a rollback returns the number. Slower than a sequence, and correct, which is the trade that matters when a tax authority is the audience. 
-- Gapless allocation, inside the receipt-creating transaction
UPDATE receipt_sequences
   SET last_number = last_number + 1
 WHERE gym_id = ? AND financial_year = ?
RETURNING last_number;                 -- row-locked; rolls back with the transaction

-- Only one active membership per member (FR-BIL-02)
CREATE UNIQUE INDEX uq_memberships_active
    ON memberships (member_record_id) WHERE state = 'ACTIVE';

-- FR-BIL-10: the balance cache can never go negative or exceed the total
ALTER TABLE pt_packages ADD CONSTRAINT ck_pt_packages_credits
    CHECK (credits_remaining >= 0 AND credits_remaining <= credits_total);

-- A payment may never be over-allocated across its targets
-- (sum of allocations <= payment amount) — enforced in service under lock,
-- since SQL cannot express a cross-row aggregate constraint.

How capacity is actually enforced. booked_count is denormalised onto sessions specifically so that a CHECK constraint can police it. The booking transaction locks the session row, increments the counter, and inserts the booking; if the increment would breach capacity the constraint aborts the whole transaction. This is what makes NFR-PRF-05 a database guarantee rather than an application intention — twenty concurrent requests for one remaining place produce exactly one booking, with no application-level coordination. 
-- The constraint that cannot be argued with
ALTER TABLE sessions ADD CONSTRAINT ck_sessions_capacity
    CHECK (booked_count >= 0 AND booked_count <= capacity);

-- FR-CLS-06: one live booking per person per session. Partial unique index,
-- so a cancelled booking does not block re-booking the same session.
CREATE UNIQUE INDEX uq_bookings_live
    ON bookings (session_id, user_id)
 WHERE state IN ('BOOKED','WAITLISTED');

-- FR-CLS-14: no double-booked trainer or room. GiST exclusion over time ranges —
-- the database refuses overlap outright rather than the application checking for it.
ALTER TABLE sessions ADD CONSTRAINT ex_sessions_trainer_overlap
    EXCLUDE USING GIST (
        trainer_user_id WITH =,
        tstzrange(starts_at, ends_at) WITH &&
    ) WHERE (state <> 'CANCELLED');

-- FR-CLS-07: waitlist order is unique within a session
CREATE UNIQUE INDEX uq_bookings_waitlist_position
    ON bookings (session_id, waitlist_position) WHERE state = 'WAITLISTED';

The EXCLUDE USING GIST constraint requires the btree_gist extension. It is worth enabling for this one constraint alone: trainer double-booking is otherwise a check that must be remembered in every code path that creates or reschedules a session, and forgetting it produces a trainer expected in two rooms at once.

16. Row-Level Security Application

Three policy shapes cover all 74 tables. Every table gets exactly one, in the same migration that creates it (LB-ENG-1.0 §6).

ShapeApplies toRule
A — gym + locationThe majority: check_ins, bookings, sessions, memberships, payments, leads …Super Admin bypass, or matching gym_id and either gym-wide scope or a matching location_id.
B — gym onlyGym-wide entities: plans, class_types, routines, message_templatesSuper Admin bypass, or matching gym_id. No location clause — these are gym-wide by definition (FR-ORG-12).
C — user-ownedPersonal data: fitness_profiles, body_metrics, workout_logs, health_screeningsOwn rows always; otherwise only if the caller administers or is assigned to that user's location. This is where the permission matrix of LB-ENG-1.0 §13 is enforced at the data layer.
 
-- Shape A, the standard case
CREATE POLICY p_bookings_isolation ON bookings USING (
    current_setting('app.is_super_admin', true)::boolean IS TRUE
 OR (gym_id = current_setting('app.gym_id', true)::uuid
     AND (current_setting('app.gym_wide', true)::boolean IS TRUE
          OR location_id = ANY(string_to_array(
               current_setting('app.location_ids', true), ',')::uuid[])))
);

-- The exception: exercises, where NULL gym_id means the global catalogue.
-- Omitting the IS NULL branch yields an empty exercise library — an easy
-- mistake with a confusing symptom, so it has its own test.
CREATE POLICY p_exercises_isolation ON exercises USING (
    gym_id IS NULL
 OR current_setting('app.is_super_admin', true)::boolean IS TRUE
 OR gym_id = current_setting('app.gym_id', true)::uuid
);
Tables deliberately exempt from RLS. users (a person may belong to several gyms; scoping happens through role_grants and member_records), subscription_offerings and content_pages (platform-wide), muscle_groups, equipment and foods (global reference data), and job_queue (accessed only by workers using a dedicated role). Each exemption is a deliberate decision recorded in the migration that creates the table, never an omission — and the isolation test suite asserts the exempt list explicitly, so adding a table to it requires changing a test.

20. Appendix A — Deviations from Earlier Documents

DeviationEarlierNow, and why
Role grant location scopeLB-ARCH §5.2 sketched location_ids uuid[]role_grant_locations junction table. An array cannot carry a foreign key, so it will eventually reference a deleted location; the junction gives referential integrity, an indexed reverse lookup, and RESTRICT protection when closing a location. The RLS context builds its CSV from this table once per request.
Booking uniquenessLB-ARCH §5.2 used UNIQUE NULLS NOT DISTINCTPartial unique index on live states. Clearer intent, works on any Postgres version, and correctly permits re-booking after cancellation.
No members tableImplied by the SRS's languageA member is a user with a MEMBER grant. member_records holds only the per-gym commercial facts. This is what lets staff train without a second account (§2.1).

PostGIS dependencyNot mentioned in LB-ARCHAdded. Geofence distance and public proximity search both need real geography; approximating in application code is slower and wrong at the edges.
