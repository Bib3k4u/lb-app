1. Principles and How Rules Are Enforced

1.1 Why this document is short on style and long on safety

Most of what is usually called a coding standard — brace placement, import order, line length — is settled here by running a formatter and never discussing it again. Spotless and Prettier reformat on commit; nobody reviews whitespace. What remains is the small set of rules where getting it wrong produces a defect that testing will not catch and a reviewer will not notice.

This system has an unusual concentration of those. Row-Level Security fails open when misconfigured, which means a broken isolation boundary looks exactly like a working one until a gym sees another gym's members. A media upload with the wrong delivery type produces a permanent public URL for a member's receipt or identity document. A SET where SET LOCAL belonged leaks tenant context between pooled connections. None of these throw an exception. All of them pass a happy-path test.

Section 4 collects those into five rules. If you read nothing else in this document, read that.

1.2 Rule categories

MarkingMeaning
AUTOMATEDEnforced by a tool in CI. Violating it fails the build. Preferred wherever a rule can be expressed mechanically — a convention nothing enforces decays within months.
REVIEWChecked by a human at pull request. Kept deliberately few, because attention is finite and spending it on formatting means not spending it on authorisation.
CRITICALA rule whose violation is a security or data-integrity defect. These are both automated and reviewed, and they are the only rules in this document that may never be waived for expedience.

1.3 Principles

IDPrincipleIn practice
ENG-01Make the wrong thing hard to writePrefer a design where the unsafe path does not compile or does not exist over one where it is merely discouraged. A MediaService that requires a sensitivity argument beats a comment asking people to remember.
ENG-02Automate the rule or drop itIf a convention cannot be machine-checked and is not security-critical, it is a preference, not a standard. Write it down only if it earns the attention.
ENG-03Explicit over cleverThis codebase will be read by its author months later and by an AI agent with no memory. Obvious code with a boring name beats a concise idiom that needs explaining.
ENG-04The test suite is the specificationRequirements traceability lives in test names. A test called locationAdminCannotReadSiblingLocationMembers is the executable form of NFR-SEC-01a and is what makes the claim defensible.
ENG-05One way to do each thingOne error model, one pagination shape, one way to acquire tenant context, one way to enqueue a job. Variation without reason is a cost with no benefit.
ENG-06Fail closed, loudlyMissing authorisation context yields zero rows and an error, never an unfiltered query. Ambiguity resolves toward refusal.

2. Repository and Project Structure

2.1 One repository

A single repository holds the backend, the mobile app, the web console and infrastructure. The decisive reason is the generated API client: backend and clients change together, and a monorepo lets one pull request carry an endpoint change and the regenerated client that consumes it. Split repositories would make that two coordinated merges and an interval during which they disagree.

limitbeyond/
├── backend/                  // Spring Boot, Maven
├── mobile/                   // React Native + Expo
├── web/                      // React + Vite admin console
├── packages/api-client/      // GENERATED from OpenAPI — never hand-edited
├── infra/                    // Dockerfiles, compose, deploy scripts
├── docs/                     // SRS, architecture, this document, ADRs
├── .github/workflows/        // CI pipelines
└── CLAUDE.md                 // agent ruleset — Appendix C

2.2 Backend package structure

Packages follow the ten architectural modules of LB-ARCH-1.0 §4.3, not technical layers. A module owns its controllers, services, entities and repositories together; there is no global controllers package. This is what lets Spring Modulith verify boundaries at build time.

com.limitbeyond
├── platform/      identity/      org/         people/      billing/
├── attendance/    scheduling/    training/    engagement/  insights/
└── shared/        // cross-cutting only: audit, error model, RLS context, job queue

// Inside every module, the same shape:
attendance/
├── AttendanceModule.java        // @ApplicationModule — declares allowed dependencies
├── api/                         // PUBLIC: what other modules may use
│   ├── AttendanceFacade.java    //   interface, the only entry point
│   └── CheckInRecorded.java     //   published event (record)
├── web/                         // package-private: controllers, request/response DTOs
├── domain/                      // package-private: entities, value objects, invariants
├── internal/                    // package-private: service implementations
└── persistence/                 // package-private: repositories
Rule ENG-2.1 — Only api/ is publicAUTOMATED
Every class outside a module's api/ package is package-private. A module reaching into another's domain, internal or persistence fails the Modulith verification test and the build. Why: boundaries decay silently under delivery pressure, and restoring them later costs far more than maintaining them. Making the compiler the enforcer removes the judgement call entirely.

Rule ENG-2.2 — Route files contain no logicREVIEW
A file under app/ renders a screen component from features/ and nothing else — no data fetching, no business logic, no conditionals beyond a permission guard. Why: routes are the hardest part of the app to test; keeping them empty makes the testable part the part that matters.

3. Backend Standards — Java and Spring

3.1 Layering

Three layers, one direction of travel: web → service → persistence. Skipping a layer is not permitted, and neither is travelling back up.

LayerMay doMust never do
webDeserialise and validate input, call exactly one service method, map the result to a response DTO, set the status code.Touch a repository. Contain business rules. Open a transaction. Decide authorisation.
serviceEnforce authorisation, own the transaction boundary, apply business rules, orchestrate repositories, publish events, enqueue jobs.Reference HttpServletRequest, response DTOs, or any web type. Return entities outside the module.
persistenceQuery and persist. Own no logic beyond query construction.Call a service. Perform authorisation. Be referenced from web.
Rule ENG-3.1 — Authorisation lives in the service layerCRITICAL
Every service method that reads or writes tenant data begins with an authorisation check naming the permission and the location it applies at. Not in the controller — controllers are added, forgotten and duplicated; a service method is the single chokepoint every caller passes through. Why: FR-AUTH-28 requires authority be evaluated per location. One central evaluation is auditable; scattered annotations are not.

3.2 Reference implementation — controller

@RestController
@RequestMapping("/api/v1/locations/{locationId}/check-ins")
@RequiredArgsConstructor
class CheckInController {                      // package-private: nothing outside needs it

    private final AttendanceFacade attendance;

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    CheckInResponse record(@PathVariable LocationId locationId,
                           @Valid @RequestBody CheckInRequest request) {
        // No logic. No authorisation. No repository. One call, one mapping.
        return CheckInResponse.from(
            attendance.recordCheckIn(locationId, request.toCommand()));
    }
}

3.3 Reference implementation — service

@Service
@RequiredArgsConstructor
class CheckInService implements AttendanceFacade {

    private final AttendanceRepository attendanceRepo;
    private final MembershipFacade memberships;      // another module's api/ — allowed
    private final JobQueue jobs;
    private final AuthContext auth;

    @Override
    @Transactional                                     // the ONLY place a transaction starts
    public CheckIn recordCheckIn(LocationId locationId, RecordCheckInCommand cmd) {

        auth.require(Permission.RECORD_CHECK_IN, locationId);   // ENG-3.1, always first

        // Idempotency before side effects — a replayed offline submission
        // must return the original result, not create a second row (FR-ATT-05).
        Optional<CheckIn> existing =
            attendanceRepo.findByUserAndIdempotencyKey(cmd.userId(), cmd.idempotencyKey());
        if (existing.isPresent()) return existing.get();

        Membership membership = memberships.activeFor(cmd.userId(), locationId)
            .orElseThrow(() -> new MembershipNotActiveException(cmd.userId()));

        // Domain invariants belong to the domain object, not to this method.
        CheckIn checkIn = CheckIn.record(cmd, membership, auth.currentUser());

        attendanceRepo.save(checkIn);

        // Enqueued IN THIS TRANSACTION: a rollback removes the job too (ADR-09).
        jobs.enqueue(new RecalculateStreak(cmd.userId()));

        return checkIn;
    }
}

3.4 Transactions

RuleReason
@Transactional on service methods onlyControllers and repositories must not define transaction scope. One boundary per business operation keeps the atomicity story legible.
Never call an external service inside a transactionTwilio, Cloudinary and Expo calls hold a database connection open for the duration of a network round trip. Enqueue a job instead; the job runs after commit.
Use lockForUpdate for contended rowsSession capacity and credit balances are contended. A read-then-write without a lock is a lost update under concurrency, which is exactly what NFR-PRF-05 forbids.
Read-only operations use @Transactional(readOnly = true)Signals intent and lets the driver optimise. It is also where the RLS context is set, so even reads must be transactional.

3.5 Error handling

One exception hierarchy, one response shape. Errors carry a stable machine-readable code; messages are for humans and may change without notice.

// shared/error/DomainException.java
public abstract class DomainException extends RuntimeException {
    public abstract ErrorCode code();      // stable, documented, client-switchable
    public abstract HttpStatus status();
}

// One handler, RFC 7807 Problem Details, for the entire application
@RestControllerAdvice
class GlobalExceptionHandler {

    @ExceptionHandler(DomainException.class)
    ProblemDetail handle(DomainException ex) {
        ProblemDetail pd = ProblemDetail.forStatus(ex.status());
        pd.setTitle(ex.code().title());
        pd.setDetail(ex.getMessage());
        pd.setProperty("code", ex.code().name());           // clients switch on this
        pd.setProperty("correlationId", MDC.get("correlationId"));
        return pd;
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail handleUnexpected(Exception ex) {
        log.error("Unhandled exception", ex);               // full detail to logs…
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
        pd.setDetail("An unexpected error occurred.");      // …nothing internal to the client
        pd.setProperty("correlationId", MDC.get("correlationId"));
        return pd;
    }
}
Rule ENG-3.2 — Never leak internals in an error responseCRITICAL
Stack traces, SQL, class names and upstream provider messages never reach a client. The correlation ID is the bridge: the user reports it, and it locates the full detail in the logs. Why: error responses are the most reliable reconnaissance surface an attacker has, and the most common accidental disclosure path.

3.6 Validation — two distinct kinds

KindWhereWhat it checks
Input validationRequest DTO, Bean Validation annotationsShape: required, length, format, range. Cheap, mechanical, rejects malformed requests with 400 before any logic runs.
Domain invariantsInside the domain object, in its constructor or factoryTruths that must hold for the object to be valid at all: credits never negative, a session's end after its start, a booking's location matching its session's. Enforced at construction so an invalid instance cannot exist.
 
// Domain invariant enforced at construction — an invalid PtPackage is unconstructible
public record PtPackage(PackageId id, UserId member, TrainerId trainer,
                         int creditsTotal, int creditsRemaining, LocalDate validUntil) {
    public PtPackage {
        if (creditsRemaining < 0)
            throw new IllegalArgumentException("credits cannot be negative");
        if (creditsRemaining > creditsTotal)
            throw new IllegalArgumentException("remaining cannot exceed total");
    }
    public PtPackage consumeOne() {
        if (creditsRemaining == 0) throw new NoCreditsRemainingException(id);
        return new PtPackage(id, member, trainer, creditsTotal, creditsRemaining - 1, validUntil);
    }
}

Note the database also carries CHECK (credits_remaining >= 0). The redundancy is deliberate: the domain object gives a good error message, the constraint guarantees the rule even if a future code path forgets it.

3.7 Nullability, immutability and naming

RuleReason
Optional for return values, never for fields or parametersIts purpose is expressing "may be absent" at a call site. As a field it adds indirection and breaks serialisation.
Records for DTOs, commands, events and value objectsImmutable by construction, concise, with correct equals for free. Use a class only when JPA requires one.
Typed identifiers, not raw UUIDUserId and LocationId are different types, so passing one where the other belongs will not compile. Given how many identifiers this domain juggles, this catches a real and otherwise silent class of bug.
No abbreviations in namesmembership, not mbrshp. The cost is keystrokes; the benefit is every future reader, human or agent.
Boolean methods read as assertionsisActive(), hasCreditsRemaining(), canBookAt(location).
Test names are sentenceslocationAdminCannotReadSiblingLocationMembers(). Per ENG-04, the test list should read as a specification.

4. The Five Non-Negotiables

Each of these, if broken, produces a defect that compiles, passes ordinary tests, and shows no symptom until it matters. They are the reason this document exists.

NN-1 — Use SET LOCAL, never SET, for RLS context.
Connections are pooled. Plain SET persists on the connection after your request completes, so the next request — potentially serving a different gym — inherits your tenant context and reads their data. SET LOCAL is transaction-scoped and discarded on commit or rollback, which is the only reason pooling is safe here. Never write a bare SET against the application datasource.
NN-2 — The application never connects as the table owner.
A table owner bypasses RLS policies by default. If lb_app owns the tables, every policy is inert and the system appears to work perfectly while enforcing nothing. Two roles: lb_migrator owns the schema and runs Flyway; lb_app owns nothing and serves requests. Every table also carries FORCE ROW LEVEL SECURITY.
NN-3 — Sensitive media is never uploaded with Cloudinary's default type.
The default upload type yields a permanent, public, unrevocable URL. Applied to a receipt or an identity document that is a privacy breach which deleting the database row does not undo, because the URL may already be cached or shared. All uploads go through MediaService, which takes sensitivity as a required argument. There is no other upload path.
NN-4 — Store Cloudinary public_id, never a full URL.
URLs are constructed at read time. A stored URL embeds the provider in every row referencing an image, turning a provider change from a one-class edit into a data rewrite — and it bypasses the signing logic that NN-3 depends on.
NN-5 — Every tenant-scoped service method authorises before it acts.
auth.require(permission, locationId) is the first statement. RLS is the second line of defence, not the first; relying on it alone means an authorisation bug degrades silently into "returns nothing" instead of failing loudly, and write paths are not protected by read policies at all.

4.1 The RLS context implementation

// shared/rls/RlsContextAspect.java — applied to every request-bound transaction
@Aspect @Component @RequiredArgsConstructor
public class RlsContextAspect {

    private final JdbcTemplate jdbc;
    private final AuthContextProvider authProvider;

    @Before("@annotation(org.springframework.transaction.annotation.Transactional)")
    public void applyContext() {
        AuthContext ctx = authProvider.current();

        // SET LOCAL — transaction-scoped. See NN-1. A bare SET here is a data breach.
        jdbc.update("SET LOCAL app.gym_id = ?",         ctx.gymId().value());
        jdbc.update("SET LOCAL app.location_ids = ?",   ctx.locationIdsCsv());
        jdbc.update("SET LOCAL app.gym_wide = ?",       ctx.isGymOwner());
        jdbc.update("SET LOCAL app.is_super_admin = ?", ctx.isSuperAdmin());
    }
}
Why missing context is safe. The policies read current_setting('app.gym_id', true) — the true makes a missing setting return NULL rather than raising. A NULL comparison matches no rows, so a query that somehow escaped the aspect returns empty rather than unfiltered. That is ENG-06 in concrete form: the failure mode is refusal, and it is immediately obvious in a test.

5. API Design Conventions

ConcernConvention
Base path/api/v1. The version is in the path and increments only on a breaking change. Old app builds stay in circulation for weeks after a store release (NFR-MNT-04), so v1 must keep working long after v2 ships.
Resource namingPlural nouns, kebab-case: /check-ins, /pt-packages. Never verbs — the method is the verb.
Location scopingLocation-scoped resources nest under their location: /api/v1/locations/{locationId}/members. This makes the scope explicit in the route and gives the service its authorisation argument directly, rather than inferring it.
State transitionsA sub-resource, not a verb endpoint: POST /bookings/{id}/cancellation rather than /cancelBooking.
Status codes200 read, 201 create with Location, 204 delete, 400 malformed, 401 unauthenticated, 403 unauthorised, 404 absent or invisible, 409 state conflict, 422 valid but rejected by a business rule, 429 rate-limited.
404 versus 403A resource outside the caller's location scope returns 404, not 403. A 403 confirms the resource exists, which leaks the existence of another gym's data — the exact thing NFR-SEC-01a forbids.
PaginationCursor-based: ?cursor=&limit=, returning { items, nextCursor }. Offset pagination skips and duplicates rows as data shifts beneath it, which attendance and bookings do constantly.
IdempotencyIdempotency-Key header required on every POST that the mobile client may retry. The server stores it and returns the original result on replay.
DatesISO-8601 with offset, always UTC on the wire. Never a bare local date-time — a gym in a different timezone is a supported case.
MoneyInteger minor units (paise) with an explicit currency. Never a floating-point type anywhere near money.
Naming in JSONcamelCase, matching TypeScript. Configured once on the serialiser, never per-field.

6. Database Standards

RuleDetail
Namingsnake_case; plural tables (check_ins); singular columns; foreign keys <entity>_id; indexes idx_<table>_<cols>; constraints ck_/uq_/fk_.
Required columnsEvery operational table: id uuid (UUIDv7), gym_id uuid NOT NULL, location_id uuid NOT NULL, created_at, updated_at, created_by. The scoping columns are not optional — they are what the RLS policies filter on.
EnumsPostgres enum types, not strings. Adding a value is a migration, which is correct: a new booking state should be a deliberate schema decision.
Soft deletedeleted_at timestamptz on entities FR-ADM-03 covers. Never DELETE a member, payment or attendance row.
MigrationsFlyway, forward-only, one logical change each. V<n>__<description>.sql. A migration merged to main is immutable — corrections are new migrations.
Every new tableThe same migration that creates a table must enable and force RLS and attach its policy. A table without a policy is a leak waiting to happen, so the two are never separated.
No business logic in the databaseNo triggers, no stored procedures — with one exception: constraints expressing invariants (CHECK, UNIQUE, foreign keys), which are declarations rather than logic and belong there.
 
-- The standard shape of a create-table migration. Both halves, always together.
CREATE TABLE check_ins (
    id              uuid        PRIMARY KEY,
    gym_id          uuid        NOT NULL REFERENCES gyms(id),
    location_id     uuid        NOT NULL REFERENCES locations(id),
    user_id         uuid        NOT NULL REFERENCES users(id),
    occurred_at     timestamptz NOT NULL,
    method          checkin_method  NOT NULL,
    purpose         checkin_purpose NOT NULL,
    idempotency_key text        NOT NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_check_ins_idempotency UNIQUE (user_id, idempotency_key)
);

CREATE INDEX idx_check_ins_user_occurred  ON check_ins (user_id, occurred_at DESC);
CREATE INDEX idx_check_ins_gym_location   ON check_ins (gym_id, location_id);

-- Not optional, not a later migration, not a separate ticket:
ALTER TABLE check_ins ENABLE ROW LEVEL SECURITY;
ALTER TABLE check_ins FORCE  ROW LEVEL SECURITY;
CREATE POLICY p_check_ins_isolation ON check_ins USING (
    current_setting('app.is_super_admin', true)::boolean IS TRUE
    OR (gym_id = current_setting('app.gym_id', true)::uuid
        AND (current_setting('app.gym_wide', true)::boolean IS TRUE

7. Security Coding Standards

AreaStandard
SQLParameterised queries or JPA only. String concatenation into SQL fails review unconditionally.
PasswordsArgon2id via Spring Security's encoder. Never a custom hash, never MD5 or SHA for credentials.
Tokens on deviceexpo-secure-store (Keychain / Keystore). Never AsyncStorage, which is unencrypted plaintext readable on a rooted device.
SecretsInjected from Secrets Manager at runtime. Never in source, never in the image, never in application.properties. A committed secret is rotated, not deleted — git history is forever.
Rate limitingAuth, OTP issuance and check-in are rate-limited per account and per device (NFR-SEC-08). OTP is the expensive one: each request costs real money.
QR payloadsFixed and printable, but signed and location-scoped. Every scan must include device coordinates validated against the location geofence, so a photographed code cannot be used away from the gym (NFR-SEC-10).
DependenciesDependabot plus OWASP dependency-check in CI, failing the build on high severity.
CORSExplicit origin allowlist. Never * on an authenticated API.
Never logged, at any level, in any environment: passwords, OTP codes, access or refresh tokens, full mobile numbers (last four digits only), health screening content, diet plan content, Cloudinary signed URLs, and API keys. Logs are shipped to third-party services, retained for months, and read by people who have no business seeing any of it. Log the identifier, never the content. 
// WRONG — three separate disclosures
log.info("Login for {} with otp {}",
         user.phoneNumber(), otp);
log.debug("Health: {}", member.healthScreening());
// RIGHT — identifiers only
log.info("Login attempt userId={} phone=***{}",
         user.id(), user.phoneLast4());
log.debug("Health screening updated userId={}",
          member.id());

8. Mobile Standards — React Native and Expo

8.1 TypeScript

strict: true, plus noUncheckedIndexedAccess and exactOptionalPropertyTypes. any is banned and fails lint; unknown with narrowing is the escape hatch. The generated API client is the single source of server types — never hand-write an interface that mirrors a server response, because the hand-written copy is what silently drifts.

8.3 Every data screen handles four states

UI-04 requires an explicit loading, empty, error and success state on every data-bearing view. Not a convention — a component contract, so it cannot be skipped by omission.

}

8.4 The offline outbox

Only check-in and workout logging are queued (ADR-06). The rule that makes this safe is worth restating: both operations are non-contending — a check-in is an append-only fact, a workout log has exactly one author — so no conflict resolution is needed. Anything that contends for a shared resource stays online.

// lib/sync/outbox.ts
export async function enqueue<T extends OutboxOperation>(op: T): Promise<void> {
  await db.insert(outbox).values({
    id: randomUUID(),
    idempotencyKey: randomUUID(),   // generated ONCE; reused on every retry
    type: op.type,
    payload: JSON.stringify(op.payload),
    occurredAt: new Date().toISOString(),   // original time preserved — FR-ATT-07
    attempts: 0,
  });
  void drain();                      // fire and forget; UI already confirmed
}

export async function drain(): Promise<void> {
  if (!(await isOnline())) return;

  for (const item of await pendingItems()) {
    try {
      // Same key every attempt — this is what makes retry safe (FR-ATT-05)
      await api.submit(item.type, JSON.parse(item.payload), {
        idempotencyKey: item.idempotencyKey,
      });
      await remove(item.id);
    } catch (e) {
      if (isPermanent(e)) { await markFailed(item.id, e); }   // 4xx: surface to user
      else { await backoff(item); break; }                     // 5xx/network: retry later
    }
  }
}
Rule ENG-8.1 — The idempotency key is generated once, at enqueueCRITICAL
Generating a fresh key per attempt defeats the entire mechanism: each retry looks like a new operation and creates a duplicate row. The key belongs to the operation, not to the attempt. This single line is what FR-ATT-05 rests on under offline replay.

8.5 Media

All uploads go through lib/media, which requires a sensitivity argument (NN-3) and returns a public_id (NN-4). Display URLs are built with f_auto,q_auto and an explicit width, so a 12-megapixel exercise demonstration image is never downloaded whole onto a phone over mobile data. Media in scope is exercise and gym imagery, profile pictures, receipts and optional identity documents — not progress photographs, which are out of scope (§13).

9.2 The isolation suite

@SpringBootTest
@Testcontainers
class LocationIsolationTest {

    @Container
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");

    // Two gyms, two locations each — the fixture is the point. Isolation bugs
    // are invisible when only one tenant exists in the database.
    @BeforeEach void seed() { fixtures.twoGymsTwoLocationsEach(); }

    @Test
    void locationAdminCannotReadSiblingLocationMembers() {
        asLocationAdmin(GYM_A, LOCATION_A1);

        List<Member> visible = memberRepository.findAll();

        assertThat(visible).allMatch(m -> m.locationId().equals(LOCATION_A1));
        assertThat(visible).noneMatch(m -> m.locationId().equals(LOCATION_A2));
    }

    @Test
    void locationAdminCannotReadMemberFromAnotherGymEvenByDirectId() {
        asLocationAdmin(GYM_A, LOCATION_A1);
        // Direct lookup by a known id — the identifier-guessing path NFR-SEC-01a names
        assertThat(memberRepository.findById(KNOWN_MEMBER_IN_GYM_B)).isEmpty();
    }

    @Test
    void queryWithoutRlsContextReturnsNothing() {
        clearRlsContext();
        // Fails closed, per ENG-06. If this ever returns rows, RLS is misconfigured
        // and NN-2 is the first thing to check.
        assertThat(memberRepository.findAll()).isEmpty();
    }
}
This suite may never be disabled to make a build pass. It is the only evidence that the platform's central security claim is true. If it fails, the correct response is to stop and fix the isolation defect — never to @Disabled it and open a ticket.

9.3 Concurrency test — the booking race

@Test
void concurrentBookingsNeverExceedCapacity() throws Exception {
    Session session = fixtures.sessionWithCapacity(1);          // one place left
    var latch = new CountDownLatch(1);

    List<Future<BookingResult>> results = new ArrayList<>();
    try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < 20; i++) {
            UserId member = fixtures.member();
            results.add(pool.submit(() -> { latch.await();       // all start together
                return bookingService.book(session.id(), member); }));
        }
        latch.countDown();
    }

    assertThat(countOf(results, BOOKED)).isEqualTo(1);           // exactly one winner
    assertThat(countOf(results, WAITLISTED)).isEqualTo(19);      // no one lost
}

The shaded row, explained. Access is scoped to the member's own location and is audited. Measurements and weight follow the same rule for the same reason: a trainer cannot programme progressively without them.
Progress photographs are out of scope. They were the platform's most sensitive data class, they had no operational purpose, and they were the sole cause of a contradiction between NFR-PRV-02 and NFR-PRV-03. Sensitive media handling does not disappear, only shrinks: receipts and optional identity documents (FR-MEM-07) still require authenticated Cloudinary delivery. NN-3 and NN-4 stand unchanged, applied to a smaller and far less alarming set. Should photographs be wanted later, they return as a new requirement with this matrix as the starting point — not as a quiet re-enablement.

Appendix B — Definition of Done

A change is done when all of the following are true. Not most.

  1. Implements the requirement it cites, including its edge cases.
  2. All automated gates pass — no exclusions, no @Disabled, no suppressed warnings without a comment saying why.
  3. Tests exist for the failure paths, not just the success path.
  4. Where it touches tenant data, an authorisation test exists for both an in-scope and an out-of-scope caller.
  5. Where it adds a table, the isolation suite covers it.
  6. Logs carry the standard fields and leak no content.
  7. The API change is reflected in OpenAPI and the client is regenerated.
  8. Any architectural decision taken along the way is recorded as an ADR.
  9. Any SRS contradiction discovered is recorded in Appendix D rather than resolved silently in code.

## NEVER (these fail silently — no exception, no test failure, no symptom)

1. NEVER use bare `SET` for RLS context. Always `SET LOCAL`, inside a transaction.
   Plain SET persists on the pooled connection and leaks tenant context to the
   next request. This is a data breach, not a style issue.
2. NEVER connect the application as the table owner. `lb_app` owns nothing;
   `lb_migrator` owns the schema. Owners bypass RLS unless FORCE is set.
3. NEVER upload media with Cloudinary's default `upload` type when it may be
   sensitive. Receipts and ID documents use `authenticated`. All uploads go
   through MediaService, which requires a sensitivity argument.
4. NEVER store a full Cloudinary URL. Store `public_id`; build URLs at read time.
5. NEVER write a tenant-scoped service method without `auth.require(permission,
   locationId)` as its first statement.
6. NEVER log passwords, OTPs, tokens, full phone numbers, health screening or
   diet content. Log identifiers, never content.
7. NEVER return 403 for a resource outside the caller's scope — return 404.
   A 403 confirms existence and leaks another gym's data.
8. NEVER call an external service (Twilio, Cloudinary, Expo) inside a
   transaction. Enqueue a job instead.
9. NEVER generate a fresh idempotency key per retry. One key per operation.
10. NEVER use floating point for money. Integer minor units (paise) + currency.

## ALWAYS

- Create tables WITH their RLS policy in the same migration. Enable AND force.
- Include `gym_id` and `location_id` on every operational table.
- Put `@Transactional` on service methods only — never controllers, never repos.
- Enqueue jobs inside the same transaction as the change that triggers them.
- Lock contended rows (session capacity, PT credits) with `lockForUpdate`.
- Enforce domain invariants in the domain object's constructor.
- Give every data screen loading / empty / error / success states.
- Name tests as sentences: `locationAdminCannotReadSiblingLocationMembers`.

## Module structure

Ten modules: platform, identity, org, people, billing, attendance,
scheduling, training, engagement, insights (+ shared).

Only `api/` is public. `web/`, `domain/`, `internal/`, `persistence/` are
package-private. Cross-module access goes through the other module's facade
interface or a published event. Modulith verification fails the build otherwise.

`training` serves EVERY role, not just members — that is FR-PFP-01. No method
in it takes a role parameter or branches on one. A Gym Owner logging their own
sets uses the identical code path a member does.

## Permissions

Five roles: SUPER_ADMIN, GYM_OWNER, LOCATION_ADMIN, TRAINER, MEMBER.
Authority is a set of grants, each scoped to a gym and named locations.
Effective authority = union of grants EVALUATED PER LOCATION — never the
maximum applied everywhere.

Super Admin has full operational reach across all gyms but NO data access
beyond a Gym Owner's. Owning the platform confers reach, not depth.

Progress PHOTOGRAPHS are out of scope — do not build upload, storage or
display for them. Progress tracking is weight, measurements, body fat,
personal records, volume trends and streaks only.

## When unsure

Check the specs before inventing. If a requirement seems contradictory, say so
and ask — do not resolve it silently in code. If a rule above blocks something
that seems necessary, that is the signal to ask, not to work around it.
