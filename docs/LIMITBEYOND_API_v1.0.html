1. Introduction and Design Stance

1.1 What this API serves

One HTTP interface serves three consumers, and the differences between them shape the design more than any style preference:

ConsumerCharacteristicsWhat that demands
Mobile app
all five roles		Intermittent connectivity, old builds in circulation for weeks after a store releaseIdempotent writes, small payloads, and a version that keeps working long after the next one ships (NFR-MNT-04)
Web console
admins		Good connectivity, large lists, bulk operations, exportsCursor pagination, filtering, and asynchronous report generation
Public site
unauthenticated		Server-rendered at build and revalidation time; crawled by search enginesCacheable reads, stable shapes, and exactly one narrow write path

1.2 Three rules that outrank style

Most API conventions are arbitrary but worth being consistent about. Three here are not arbitrary, because getting them wrong produces a security or correctness defect rather than an inelegant interface.

1 — A resource outside the caller's scope returns 404, never 403. A 403 confirms that the resource exists. Applied across a multi-tenant directory, that turns identifier enumeration into a census of every gym's members. NFR-SEC-01a forbids exactly this, so the absence of authority and the absence of the resource must be indistinguishable to the caller. The one exception is an action on a resource the caller can see but may not perform — that is a genuine 403.
2 — Every retryable write requires an Idempotency-Key. A network failure is ambiguous: the client cannot distinguish a request that never arrived from one that succeeded but whose response was lost. Without a key, retrying risks a duplicate check-in or a double-charged payment and not retrying risks losing it. With one, the client may retry freely. This is also how FR-ATT-05's duplicate-rejection requirement is met under offline replay — one mechanism satisfying a correctness requirement and an availability requirement at once.
3 — Scope is taken from the path or the token, never from the body. No endpoint accepts gymId or locationId as a request field. Both are derived server-side from the route and the caller's grants. A body-supplied tenant identifier is a cross-tenant write waiting to happen, and it is the specific defect the public lead endpoint would otherwise be vulnerable to (§15.3).

2. Conventions

2.1 Versioning and base path

All authenticated endpoints sit under /api/v1; the public surface under /api/v1/public. The major version is in the path and increments only for a breaking change. Additive changes — a new optional field, a new endpoint, a new enum value in a response — ship within v1 and clients must tolerate them.

Why path versioning rather than a header. App-store review means an old mobile build stays in circulation for weeks after its replacement ships (NFR-MNT-04). A version visible in the URL is trivially routable, cacheable and greppable in logs when diagnosing which build a failing client is running. Header negotiation is more elegant and less operable.

2.2 Naming and resource shape

RuleExample
Plural nouns, kebab-case/check-ins, /pt-packages, /class-types
Never a verb in a pathThe method is the verb.
State transitions are sub-resourcesPOST /bookings/{id}/cancellation — not /cancelBooking
Location-scoped resources nest/locations/{locationId}/members — the scope is in the route, which is also what the service authorises against
Gym-wide resources do not nest/plans, /class-types — gym comes from the token (FR-ORG-12)
Own data uses /me/me/workouts, /me/progress — every account has these, whatever its role (FR-PFP-01)
JSON fields are camelCaseConfigured once on the serialiser, never per field
/me is not a convenience alias. It is the API's expression of the dual-facet model. GET /me/workouts is the same endpoint for a member, a trainer and a gym owner, and it takes no role parameter. Had personal training data been nested under /members/{id}, staff would have needed a member identity to use it — which is precisely the modelling mistake FR-PFP-01 exists to prevent.

2.4 Errors — RFC 7807 Problem Details

One shape for every failure, produced by a single handler (LB-ENG-1.0 §3.5). Clients switch on code; detail is for humans and may change without notice.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type":          "about:blank",
  "title":         "No sessions remaining",
  "status":        422,
  "detail":        "This personal training package has no sessions left.",
  "code":          "NO_CREDITS_REMAINING",   // stable — switch on this
  "correlationId": "01J9F2K7X3QW8M4N"          // quote to find it in the logs
}

Validation failures add a fields array naming the offending field and a message — never the submitted value, which may be personal data and would then be logged by whatever consumes the response.

{
  "title":  "Validation failed",
  "status": 400,
  "code":   "VALIDATION_FAILED",
  "fields": [
    { "field": "phone", "message": "must be a valid Indian mobile number" }
  ]
}
What never appears in an error response: stack traces, SQL, class names, upstream provider messages, or the value that failed validation. Error responses are the most reliable reconnaissance surface an attacker has. The correlation ID is the bridge — the user quotes it, and it locates the full detail in the logs.

2.5 Pagination — cursor, not offset

GET /api/v1/locations/{locationId}/members?limit=50&cursor=eyJpZCI6IjAxSjl...

{
  "items": [ … ],
  "nextCursor": "eyJpZCI6IjAxSjlGMks3WDNRVzhNNE4ifQ",  // null on the last page
  "hasMore": true
}
ParameterBehaviour
limitDefault 25, maximum 100. A larger value is clamped, not rejected.
cursorOpaque. Clients must not parse or construct one — its encoding is free to change.
Why not ?page=2. Offset pagination re-runs the query and skips rows, so anything inserted or deleted between page one and page two shifts every subsequent row — items get duplicated across pages or skipped entirely. Attendance and bookings change constantly while an admin is paging through them, so offsets would be visibly wrong in exactly the lists people use most. Cursors anchor to a row and are stable under concurrent writes.

2.6 Filtering and sorting

GET /locations/{id}/members?status=ACTIVE&expiringBefore=2026-10-31&sort=-joinedOn
GET /locations/{id}/check-ins?from=2026-09-01&to=2026-09-30&purpose=SHIFT

Filters are explicit named parameters, never a generic query language. Each is a documented, indexed access path; an arbitrary filter expression would let a client construct a query that scans a ten-million-row table. Sorting uses sort=field or sort=-field for descending, restricted to an allow-list per endpoint.

2.7 Idempotency

Required on every POST a client may retry: check-ins, workout logs, bookings, payments, leads. Optional and harmless elsewhere.

POST /api/v1/locations/{locationId}/check-ins
Idempotency-Key: 9f1c8b30-6a4e-7c21-b8d5-1e2f3a4b5c6d
SituationResponse
First requestProcessed normally. Key and outcome recorded.
Replay, same key, same payloadThe original response, with Idempotency-Replayed: true. No second row is created.
Same key, different payload409 IDEMPOTENCY_KEY_REUSED. Reusing a key for a different operation is a client bug and silently accepting it would hide it.
Key absent where required400 IDEMPOTENCY_KEY_REQUIRED.
The key belongs to the operation, not the attempt. A client that generates a fresh UUID per retry defeats the entire mechanism — each retry looks like a new operation and creates a duplicate. This is the single most consequential client-side rule in the API, and it is why the mobile outbox generates its key once at enqueue and reuses it across every attempt.

Keys are retained 24 hours, which comfortably exceeds any plausible offline queue.

3. Authentication and Authorisation

3.1 Token model

TokenLifetimeContents and handling
Access15 minutesJWT carrying sub, account state, and the account's role grants with their location scope. Sent as a bearer token. Short-lived because it cannot be revoked before expiry.
Refresh60 daysOpaque, stored server-side hashed, revocable individually or wholesale. Exchanged for a new pair; rotated on every use.

Clients store both in the device secure store — Keychain or Keystore, never AsyncStorage or localStorage (LB-ENG-1.0 §7).

3.2 Grants in the token

{
  "sub":   "01J9F2K7X3QW8M4N5P6R7S8T9V",
  "state": "ACTIVE",
  "grants": [
    { "role": "TRAINER",        "gymId": "01J9…A1",
      "locationIds": ["01J9…L1", "01J9…L2"], "gymWide": false },
    { "role": "LOCATION_ADMIN", "gymId": "01J9…A1",
      "locationIds": ["01J9…L1"],           "gymWide": false }
  ],
  "exp": 1789012345
}
Read that example carefully — it is the whole authorisation model in one payload. This account is a trainer at two locations and an admin at only one. At L1 it may verify members; at L2 it may coach but not administer. Effective authority is the union of grants evaluated per location, never the maximum applied everywhere (FR-AUTH-28). Trainer + Location Admin is a first-class supported combination (FR-AUTH-26), not an edge case.

3.3 How a request is authorised

#StageWhat happens
1Token validationSignature and expiry. Failure → 401 UNAUTHENTICATED.
2Account statePENDING_VERIFICATION reaches only /me/profile and /me/status (FR-AUTH-09). Suspended or deactivated → 403.
3Gym livenessA lapsed gym past its grace period restricts administrative endpoints; members keep read access to their own data (FR-SUB-07).
4Permission checkauth.require(permission, locationId) in the service method — scope first, permission second.
5RLS contextSET LOCAL injects gym, locations and role into the transaction. Every query is filtered by the database regardless of what the code asked for.

Stages 4 and 5 are deliberately redundant. A mistake in either is caught by the other; a breach requires both to be wrong at once.

11. Training — Exercises, Workouts, Nutrition, Progress

→ 201 Created

  "publicId": "lb/receipts/01J9MD3",   // NOT a URL
  "sensitivity": "SENSITIVE" }
The API never returns a media URL. It returns a publicId. Public assets have their URL constructed client-side with transformation parameters; sensitive assets require a call to /signed-url, which the server issues only after checking authorisation and which expires in minutes. There is no url field in any response and no url column in the database — which is what makes NN-4 unbreakable rather than merely documented. Progress photographs are out of scope entirely: no purpose value accepts them.

15.2 What the public API must never expose

Member names or counts · any individual's attendance · payment or revenue figures · trainer contact details beyond what the gym published · anything belonging to a gym that is not LIVE and isPubliclyListed · internal identifiers that appear in the authenticated API.

Public responses are built from a separate projection, not by stripping fields from an internal one. Stripping is a denylist, and a denylist fails open the day someone adds a field — which is how member lists end up in a search index.

15.3 The one public write

POST /api/v1/public/leads
Idempotency-Key: 8e2d…
{
  "gymSlug":      "iron-fitness",       // slugs, NOT ids
  "locationSlug": "koramangala",
  "name":         "Rahul Menon",
  "phone":        "+919812345678",
  "interest":     "TRIAL",
  "website":      ""                    // honeypot — must be empty
}
→ 202 Accepted
{ "received": true }
This endpoint is the platform's entire unauthenticated attack surface. Four things make it defensible, and all four are required:
  • Scope from slugs, never ids. The server resolves gymId and locationId from the slugs. A body-supplied gymId would let anyone inject leads into any gym's pipeline.
  • Rate limits per IP and per phone (§2.8), with the IP stored hashed for abuse investigation rather than in the clear.
  • A honeypot field plus a minimum form-fill time. Both fail silently with 202 — telling a bot it was detected only helps it.
  • RLS cannot protect this insert, because there is no authenticated context to filter on. The service sets the scope explicitly, and that code path deserves a dedicated test.

17. OpenAPI, Clients and Deprecation

17.1 Generation

springdoc generates OpenAPI 3.1 from the controllers at /api/v1/openapi.json, with Swagger UI at /api/v1/docs in non-production environments only. The document is committed on every change so a diff shows contract changes in review.

17.2 Clients

TypeScript types and a typed client are generated from that document into packages/api-client and consumed by both the mobile app and the web console. Generated files are never hand-edited. The benefit is that a breaking backend change fails the client build in CI rather than surfacing as a runtime error in a member's hands — which is most of what a shared-language backend would have given, recovered without abandoning Java (ADR-13).

17.3 Deprecation policy

StageWhat happens
AnnounceEndpoint returns Deprecation: true and a Sunset date. Marked deprecated in OpenAPI, so the generated client warns at compile time.
Minimum notice90 days. Long enough that a user who has not opened the app in two months still has a working build when they do.
MonitorUsage tracked by client version. Removal happens when traffic reaches zero, not merely when the date passes.
RemoveIn the next major version. Never within v1.

Additive changes are not deprecations and need no notice: new optional request fields, new response fields, new enum values, new endpoints. Clients must ignore unknown response fields and tolerate unknown enum values — a client that crashes on a new enum value is the reason APIs stop evolving.

Keeping this document honest. The generated OpenAPI document is the contract; this is the reasoning around it. When an endpoint changes, change both in the same pull request — a specification that describes an API the code no longer implements is worse than none, because it is believed. The parts most worth re-reading before adding an endpoint are §1.2 (the three rules that outrank style) and §2.7 (idempotency), because both describe mistakes that are invisible in testing and expensive in production.
