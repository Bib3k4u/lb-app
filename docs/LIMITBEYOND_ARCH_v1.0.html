1. Introduction and Approach

1.1 Purpose

This document specifies the technical architecture for LIMITBEYOND: the technology stack, the internal structure of the codebase, the data and security design, the mobile application architecture, and how the system is deployed and operated. It is the direct successor to LB-SRS-1.1 and assumes its requirements as given.

It is written to be actionable. Where a choice has a non-obvious implementation consequence — connection pooling interacting with row-level security, say, or idempotency keys being what makes offline sync safe — the consequence is stated here rather than left to be discovered during the build.

1.2 Relationship to the SRS

The SRS defines 21 functional modules and roughly 200 numbered requirements. Three of its requirements shape this architecture more than the rest, and each is answered by a specific decision recorded below:

RequirementWhat it demandsArchitectural answer
NFR-SEC-01aA Location Admin must never reach a sibling location's data, by any interface including exports and identifier guessing.PostgreSQL Row-Level Security (ADR-04). Isolation is a database policy, not a convention the application is trusted to follow.
NFR-PRF-05Class booking must never oversell a session under concurrent demand.A single transactional authority — one Postgres database, one @Transactional boundary, a unique constraint doing the enforcing (ADR-03, ADR-05).
FR-ATT-07A check-in attempted without connectivity must be queued and submitted on reconnection.Client-side SQLite outbox with idempotency keys (ADR-06), on the device where the connectivity problem actually is.

1.3 Guiding Principles

IDPrincipleWhat it means in practice
PRN-01Correctness before speedBookings, credits, payments and receipts are money and trust. Where the two conflict, transactional correctness wins — and at this scale the conflict is almost always imaginary, because the database is never the bottleneck (see ADR-05).
PRN-02Enforce at the lowest layerA rule enforced in the database cannot be forgotten by an endpoint. A rule enforced in a shared filter cannot be forgotten by a controller. Push every invariant as far down as it will go.
PRN-03Boring technology, deliberatelyOne language, one database, one deployable. Novelty is spent only where the problem genuinely demands it. A solo or small team's scarcest resource is attention, not compute.
PRN-04Defer distributionNothing is split into a separate service until a specific, measured pressure requires it. Distributed systems are a cost paid daily for a benefit realised rarely.
PRN-05Every external service is optionalSMS, push, WhatsApp and AI providers can each be unavailable without core operations failing. This is a requirement (NFR-AVL-04) and an architectural constraint on how integrations are written.
PRN-06Decisions carry expiry conditionsEvery ADR names what would make it wrong. A choice appropriate for a development phase is recorded as such, with the trigger for revisiting it, rather than silently hardening into permanence.

1.4 Conventions

Decisions are recorded as Architecture Decision Records: ADR-nn, each with context, the decision, the alternatives considered, consequences, and a revisit trigger. An ADR marked Rejected records an option that was considered and declined, with the reasoning — these are as valuable as the accepted ones, because they stop settled questions being reopened without new evidence.

Requirement identifiers in the form FR-XXX-nn and NFR-XXX-nn refer to LB-SRS-1.1.

3. Architecture Decision Records

ADR-01  ·  Modular monolith, not microservicesACCEPTED
Context
The SRS defines 21 modules. The instinct to map modules onto services is strong and, here, wrong.
Decision
One Spring Boot application, one database, one deployable, with module boundaries enforced at build time by Spring Modulith. Modules communicate through published interfaces and in-process events, never by reaching into each other's internals.
Why
Booking a class touches session capacity, the member's entitlement, their class-pack balance and the notification queue. In a monolith that is one transaction and it either happens or it doesn't. Across services it is a distributed transaction, a saga, and a compensating-action path for every failure mode — for a small team, with no operational platform, and no scaling pressure that would justify it.
Consequences
Deployment is trivial. Refactoring across module boundaries stays cheap. The whole application scales as a unit, and a build failure blocks everything — acceptable at this size.
Revisit if
One module develops a genuinely different scaling profile (AI inference is the likeliest candidate), or the team grows past the point where a single codebase causes contention.
ADR-02  ·  Java 21 and Spring Boot for the backendACCEPTED
Decision
Java 21 (LTS) with Spring Boot 3.3+, built with Maven, as in limitbeyond2.0.
Why
Three reasons in order of weight. The team already knows it and has it working. @Transactional is precisely the tool the booking, credit-decrement and payment requirements need. Spring Security is flexible enough to express the role × location authorisation model, which is bespoke enough that most frameworks would fight it.
Alternatives
NestJS / TypeScript — would share a language with React Native, a real benefit, recovered here instead by generating TypeScript clients from OpenAPI (ADR-13). Not worth discarding existing expertise. Go — leaner runtime, faster start, but a smaller ecosystem for this domain and a new language to learn while also learning the domain.
Consequences
A JVM baseline of roughly 300–500MB constrains instance sizing. Cold start is measured in seconds, so the deployment model must keep an instance warm — which it does. Java 21 virtual threads let the bursty 6am check-in load be handled with ordinary blocking code, no reactive programming required.
Revisit if
Never, absent a team composition change. This is a settled decision.
ADR-03  ·  PostgreSQL as the single system of recordACCEPTED
Decision
PostgreSQL 16 holds all operational data. The predecessor's MongoDB is not carried forward.
Why
The domain is relational to its core — role grants against locations, bookings against sessions against capacity, credits drawn against packages, payments allocated against memberships. Every one of these is a constraint the database can enforce, and every one of them is a bug waiting to happen if it cannot. Row-Level Security additionally provides a direct answer to the hardest security requirement (ADR-04), which no document store offers.
Where flexibility is needed
JSONB columns carry genuinely variable structures — health screening answers, AI generation payloads, notification template variables — giving document-style flexibility exactly where it earns its place, without giving up constraints everywhere else.
Consequences
Schema changes require migrations, which is a feature: the schema is reviewed, versioned and reversible. Nothing migrates from MongoDB (ADR-11), so there is no dual-model period.
ADR-04  ·  Row-Level Security for gym and location isolationACCEPTED
Context
NFR-SEC-01a requires that a Location Admin cannot reach a sibling location's data by any interface. RSK-06 names cross-location leakage the most damaging possible defect and directs that isolation be enforced at the data access layer rather than per endpoint.
Decision
Isolation is a set of Postgres RLS policies. Request context is injected per transaction; every query is filtered by the database regardless of what the application code says.
Why
Application-layer scoping is only ever as reliable as the last developer's discipline. One endpoint written in a hurry, one repository method that forgets its filter, and a gym sees another gym's members. RLS makes that class of bug structurally impossible rather than merely discouraged.
Consequences
Two critical implementation constraints follow, detailed in §5.3: the application's database user must not own the tables, and context must be set with SET LOCAL inside a transaction. Getting either wrong silently disables the protection.
Verification
A standing Testcontainers suite attempts cross-location and cross-gym access through every repository and asserts empty results. This suite is the evidence for NFR-SEC-01a and must never be skipped.
ADR-05  ·  Server-side SQLite write buffer in front of PostgresREJECTED
Proposal
Accept complex PUT/POST requests into a server-local SQLite file, acknowledge immediately, and synchronise to Postgres in the background — for speed on write-heavy operations.
Decision
Rejected. Recorded here in full because the underlying instinct is sound and will recur; it is the tier that is wrong, not the idea.
The arithmetic
NFR-PRF-02 budgets 2000ms for an end-to-end check-in on a 3G connection. Of that, mobile network round trip consumes 100–300ms, serialisation 5–20ms, authorisation 1–5ms, business logic 1–10ms — and the Postgres insert 1–5ms. The database write is roughly 0.25% of the budget. Substituting SQLite saves single-digit milliseconds on a quarter-second request.
What it costs
(1) Horizontal scaling breaks immediately — two instances hold two SQLite files, so a write to one is invisible to the other and read-after-write consistency is lost. (2) NFR-PRF-05 becomes unsatisfiable: capacity cannot be enforced across independent files, converting a solved transactional problem into an unsolved consensus one. The same applies to FR-BIL-10 credit decrements, FR-ATT-05 duplicate rejection, and FR-BIL-05 gapless receipt numbering. (3) Acknowledging before durable commit is a correctness lie on ephemeral container storage — the instance dies, the payment is gone, and the admin was told it saved. (4) It introduces a bespoke sync engine, conflict resolution, replay, dead-lettering and lag monitoring as permanent maintenance.
What was adopted instead
The valid form of the idea, in two places. On the device — SQLite as an offline outbox where the latency and connectivity problems genuinely are (ADR-06). On the server — commit to Postgres transactionally in single-digit milliseconds, then defer the expensive derived work (streak recalculation, notification dispatch, analytics rollup) to a job queue (ADR-09). This yields the perceived speed without surrendering any guarantee.
Revisit if
Measurement shows database write latency materially contributing to p95 response time. It will not at 100,000 members; the correct response then would be read replicas or partitioning, still not a write buffer.
ADR-06  ·  Client-side SQLite outbox for check-in and workout loggingACCEPTED
Decision
The mobile application holds a local SQLite database (expo-sqlite with Drizzle). Check-ins and workout set logs are written locally first, confirmed in the UI immediately, and synchronised to the server by a background task. No other operation is offline-capable.
Why these two
They share a property nothing else does: they cannot conflict. A check-in is an append-only fact about one person at one moment. A workout set log is owned exclusively by the person who created it. Neither requires arbitration against another user's concurrent action, so neither needs conflict resolution — the hard part of offline sync simply does not arise. Bookings and payments are excluded precisely because they do contend, and must be arbitrated server-side.
Why it matters
Gym floors and basements have poor signal, and these are the two things members do there. Local-first write means the UI confirms in under 16ms regardless of network, which is the actual perceived-speed win the server-side buffer was reaching for.
Consequences
Every queued operation carries a client-generated idempotency key; the server deduplicates on it, which is also how FR-ATT-05 is satisfied under retry. Deferred check-ins retain their original timestamp and are flagged as such, per FR-ATT-07.
ADR-07  ·  Neon Postgres for development, co-located in SingaporePROVISIONAL
Decision
Neon serverless Postgres during development, for its cost and free credits. Both EC2 and Neon are placed in ap-southeast-1 (Singapore).
The problem this avoids
Neon offers no Mumbai region; its nearest AWS region to India is Singapore. Placing EC2 in Mumbai and the database in Singapore puts 50–70ms of ocean between the application and its data — on every query. A request issuing five queries pays 250–350ms in network alone, breaching the 400ms p95 of NFR-PRF-01 before any code executes.
Why co-location wins
Placing both in Singapore moves the crossing from the database path to the client path. An Indian user then pays roughly 50ms extra on one hop (phone to server) rather than 60ms on five (server to database, per query). One crossing beats five, and the database round trip returns to sub-millisecond.
Implementation notes
Use Neon's pooled connection endpoint, which runs PgBouncer in transaction mode. This is compatible with the SET LOCAL pattern RLS requires (§5.3) but not with session-level prepared statements — set prepareThreshold=0 on the JDBC URL. Disable scale-to-zero on any environment where latency is measured, or the first request after idle pays a cold start of 500ms to several seconds.
Revisit when
Any of: the first paying gym goes live; sustained load makes Neon's pricing exceed RDS; or India data-residency becomes a contractual requirement. The target then is RDS Postgres in ap-south-1 (Mumbai) with EC2 alongside it, which is the lowest-latency configuration for an Indian user base. Because both are stock PostgreSQL 16, that move is a dump, restore and connection-string change — no application code is affected, which is precisely why this decision is safe to defer.
ADR-08  ·  Self-built JWT authentication with Twilio Verify for OTPACCEPTED
Decision
Spring Security issues and validates JWTs, as in limitbeyond2.0. One-time passwords for both phone and email are delivered through the Twilio Verify API.
Why not a managed identity product
The authorisation model — a set of role grants each scoped to a gym and a list of locations, feeding RLS context on every request — is bespoke. No managed product expresses it, so it would live in our database regardless, leaving a managed service to handle only the easy half while introducing a second source of truth about users to keep synchronised.
Why Verify rather than raw SMS
Verify handles code generation, expiry, retry limits and channel fallback as a service, which is meaningful security logic not worth reimplementing. It covers SMS and email through one API — matching the requirement for both — and can later add WhatsApp as an OTP channel on the same integration.
Tokens
Access tokens are short-lived (15 minutes) and carry the user's role grants; refresh tokens are long-lived, stored server-side and revocable, satisfying NFR-SEC-04 and FR-AUTH-13. Revocation on suspension is immediate for refresh, and bounded by access-token lifetime otherwise.
Development constraint
A single verified device is used for OTP throughout development. This fits a Twilio trial account, which can only deliver to pre-verified numbers, and keeps development cost at zero. The consequence to plan around: multi-user flows cannot be exercised over real OTP — verifying a trainer while signed in as an admin, or testing two members booking the same last class slot, needs more than one account. Accordingly, non-production environments expose a seeded test-user path that bypasses OTP delivery, disabled by configuration in production and covered by an automated assertion that it is off.
Dependency with lead time
Transactional SMS into India requires DLT registration under TRAI rules — sender ID and message templates registered before a single OTP can be delivered. Typically one to two weeks. Development proceeds without it on the single verified device, but no pilot with real members can start until it completes, so begin the registration early rather than at the end of Phase 1.
ADR-09  ·  Background jobs on a Postgres-backed queueACCEPTED
Decision
Deferred work runs from a job_queue table consumed with SELECT … FOR UPDATE SKIP LOCKED. No Redis, no SQS, no broker.
Why
The workload is notification dispatch, expiry sweeps, streak recalculation, WhatsApp sends and analytics rollups — thousands of jobs per day, not millions per hour. Postgres handles this comfortably, and jobs enqueued in the same transaction as the business change they follow cannot be orphaned by a rollback. That transactional coupling is a genuine correctness benefit an external broker cannot offer.
Consequences
Retries with exponential backoff, a dead-letter state after a configured attempt count, and job records retained for inspection. Scheduled sweeps run under ShedLock so that a second instance does not duplicate them.
Revisit if
Sustained job throughput exceeds a few hundred per second, or a workload needs fan-out to multiple independent consumers.
ADR-10  ·  Expo Push for notifications; no realtime tierACCEPTED
Decision
Notifications are delivered by the Expo Push Notification Service, which wraps FCM and APNs. No WebSocket or SSE infrastructure is built in any phase.
Why no realtime
Examining the SRS for genuine realtime needs finds none. Waitlist promotion (FR-CLS-08) is a push notification. Session reminders are scheduled push. A trainer's class roster is refreshed by pull-to-refresh or a short poll while the screen is open. Not one requirement needs a server-initiated stream to an open connection — so a whole tier of infrastructure, and its reconnection and scaling problems, is avoided by simply noticing that.
Consequences
Expo's receipts endpoint gives per-message delivery status, satisfying FR-NTF-06. FCM credentials and an APNs key are configured through EAS. Expo's service is a dependency, but per PRN-05 a push failure degrades only notification delivery — the in-application inbox remains the authoritative record.
ADR-11  ·  Clean start; nothing migrated from limitbeyond2.0ACCEPTED
Decision
No data is migrated. The exercise library is authored fresh against the richer model the SRS specifies — primary and secondary muscle groups, equipment, difficulty, instructions and media — rather than ported from MongoDB.
Why
The predecessor's exercise records lack the secondary muscle group, equipment and difficulty fields the new model requires, so a port would produce incomplete rows needing manual completion anyway. Authoring fresh is comparable effort and yields a clean, complete catalogue. Members, workouts, payments and history start empty; the predecessor continues running until cutover.
Consequences
This closes OPN-02. It also contradicts FR-EXR-05, which requires the predecessor's taxonomy and seed data be carried across — see Appendix B for the SRS amendment. Seed data ships as Flyway migrations so the catalogue is versioned and reproducible across environments.
ADR-12  ·  EC2 with DockerACCEPTED
Decision
The backend runs as a Docker image on a single EC2 instance (t4g.small or t4g.medium, ARM Graviton) behind Nginx terminating TLS via Let's Encrypt.
Why
Cheapest credible production-shaped topology, and the same Docker image runs unchanged on ECS or App Runner later. Nginx rather than an ALB saves roughly ₹1,400/month during development, at the cost of managing certificates — which certbot automates.
Media
Media is not stored on the instance or in S3; see ADR-15. Keeping image bytes off EC2 entirely matters on a 2GB instance.
Scaling path
Vertical first — instance size is a one-line change. Then an ALB with two instances, at which point sticky sessions are unnecessary because the application is stateless and the job queue already tolerates multiple consumers.
ADR-13  ·  REST with OpenAPI-generated clientsACCEPTED
Decision
A versioned REST API (/api/v1) documented by springdoc-generated OpenAPI 3. TypeScript clients and types are generated from that specification into both the mobile app and the web console.
Why
Generation recovers most of the type-safety benefit a TypeScript backend would have offered: the contract is single-sourced, and a breaking backend change fails the client build rather than surfacing as a runtime error in a member's hands. Versioning the path satisfies NFR-MNT-04, which matters more than usual here — app-store review latency means old app builds stay in circulation for weeks.
Alternative
GraphQL was considered and declined: it would complicate RLS context propagation and per-field authorisation for no benefit the mobile client actually needs.
ADR-14  ·  GitHub Actions and Expo EAS for deliveryACCEPTED
Decision
GitHub Actions builds, tests and deploys the backend image. Expo EAS builds and submits the mobile application, with EAS Update for over-the-air JavaScript changes.
Why OTA matters here
Apple review takes one to three days. Without over-the-air updates, a one-line JavaScript bug fix waits on that queue. EAS Update ships JS-only changes directly, reserving store submission for changes that touch native code. This materially changes how quickly production problems can be corrected.
Store constraints to plan for
An Apple Developer account ($99/year) and Google Play registration ($25 once). Apple requires a published privacy policy and a clear in-context rationale for each permission — directly relevant to health screening (FR-MEM-03) and location access for geofenced check-in (FR-ATT-02). Apps handling health-adjacent data receive closer review; the SRS position that this is fitness guidance and not medical advice (CON-07, FR-NUT-10) should be reflected in the store listing.
ADR-15  ·  Cloudinary for media, with authenticated delivery for sensitive assetsPROVISIONAL
Decision
Cloudinary stores and delivers all media during development — profile images, exercise demonstration media, generated receipts and optional identity documents — on its free tier.
Why it fits
Cloudinary is not merely storage, and the difference is what justifies it. Transformations are URL parameters, so the thumbnail and rendition pipeline that S3 would require you to build (Lambda plus an image library, invalidation, a variants table) simply does not need to exist. f_auto,q_auto serves WebP or AVIF adaptively per device, which directly serves CM-04's requirement to work on 3G-class connections — payloads shrink substantially with no application code. A CDN is included, so no CloudFront distribution is configured. And signed direct-from-client upload keeps image bytes off EC2 entirely, which is not a small thing on a 2GB instance.
The constraint that matters
Cloudinary's default upload delivery type produces permanent, public URLs. Applied naively to a receipt or an identity document, that breaches NFR-SEC-07 ("never reachable by unauthenticated URL") and NFR-PRV-02 (these are sensitive personal data). A public URL, once leaked, is permanent and unrevocable.
Required handling
Media is split by sensitivity, and the split is enforced in the upload path rather than left to the caller's judgement:
  • Sensitive — generated receipts and optional identity documents. Uploaded as type: authenticated or type: private, delivered only through signed, time-limited URLs generated server-side after an authorisation check. Never public.
  • Public — gym logos, exercise demonstration images, generic app assets. Default upload type, fully CDN-cached. These are not sensitive and benefit from aggressive caching.
Verify before Phase 2
Time-limited delivery authentication may be gated to higher Cloudinary plans. Establish which signing mechanism the account actually supports before receipts ship in Phase 1, not after. If expiring authenticated delivery proves unavailable on the plan in use, route sensitive media to S3 presigned URLs (the original ADR-12 design, unchanged and still valid) and keep Cloudinary for public assets only. The abstraction below makes that a configuration change.
Lock-in rule
Store only the Cloudinary public_id in the database — never a full URL. Every URL is constructed at read time by a MediaService abstraction that also applies the sensitivity rules above. This matters more here than it did for the database: Neon to RDS is a dump and restore because both are stock Postgres, whereas a media provider swap has no equivalent. Without this rule, provider URLs embed themselves in every row referencing an image and the migration becomes a data rewrite. With it, it is one class.
Revisit when
Free-tier credits are exhausted — note that Cloudinary credits are consumed by storage, bandwidth and transformations together, so exercise media and receipts at real volumes will pass the free tier well before storage alone would suggest. Or when sensitive-media authentication proves plan-gated. The fallback in either case is S3 with presigned URLs for private media, and the abstraction is what makes that cheap.

4.2 Why a Monolith Is the Right Shape Here

The instinct to decompose 21 modules into services is worth confronting directly, because the domain contains an operation that settles it. Consider booking the last place in a yoga class, which NFR-PRF-05 says must never oversell:

// Modular monolith — one transaction, one database, one outcome
@Transactional
public Booking book(SessionId sessionId, UserId userId) {
    Session s = sessions.lockForUpdate(sessionId);     // row lock held
    if (s.bookedCount() >= s.capacity())
        return waitlist.add(sessionId, userId);        // same transaction
    entitlements.consume(userId, s);                   // same transaction
    Booking b = bookings.create(sessionId, userId);    // same transaction
    jobs.enqueue(new BookingConfirmed(b.id()));        // same transaction
    return b;                                          // commit: all of it, or none of it
}

Split across a scheduling service, an entitlements service and a notifications service, that same operation becomes a distributed saga: a booking reserved in one service, an entitlement consumed in another, a compensating release if the second call fails, and an unresolved window in which the two disagree. Every failure path must be designed, implemented and tested. The monolith gets the same guarantee from a database transaction that has been correct since before any of us started working.

Module boundaries are still enforced — Spring Modulith fails the build when one module reaches into another's internals — so the structure that would permit later extraction is preserved without paying for distribution now.

Note on training. It deliberately serves every role, not only members — that is the architectural expression of FR-PFP-01. No method in this module accepts a role as a parameter or branches on one. A Gym Owner logging their own sets travels exactly the same code path as a member, which is the most reliable way to guarantee the SRS's dual-facet model survives implementation.

5. Data Architecture

5.1 Principles

  • Every row carries gym_id, and every operational row carries location_id — satisfying CON-01 and FR-ORG-10, and providing the columns RLS policies filter on.
  • Money and history are append-only. Payments, attendance and audit entries are never updated or deleted; corrections are new rows referencing the original (FR-BIL-12, FR-ADM-03).
  • Constraints live in the database. Capacity, uniqueness, credit non-negativity and referential integrity are enforced by Postgres, not merely by application code.
  • Identifiers are UUIDv7 — unguessable in URLs, while remaining time-ordered so index locality does not suffer as random UUIDs would.
  • Time is stored as timestamptz, always UTC, rendered in the tenant's timezone at the edge (NFR-USA-04).

5.3 Row-Level Security — the implementation that matters

RLS is the load-bearing security control in this architecture. It is also easy to configure in a way that appears to work while protecting nothing. Three details decide whether it holds.

Two database users, not one

A table owner bypasses RLS by default. If the application connects as the user that owns the tables, every policy is silently ignored and the system looks correct in testing while enforcing nothing. Two separate roles are required, and every table must additionally be marked FORCE ROW LEVEL SECURITY so the rule applies even to ownership. 
-- lb_migrator: owns the schema, runs Flyway, never serves a request
-- lb_app:      the application's runtime user, owns nothing, subject to every policy
ALTER TABLE members ENABLE ROW LEVEL SECURITY;
ALTER TABLE members FORCE  ROW LEVEL SECURITY;   -- applies to the owner too

CREATE POLICY gym_and_location_isolation ON members
  USING (
    current_setting('app.is_super_admin', true)::boolean IS TRUE
    OR (
      gym_id = current_setting('app.gym_id', true)::uuid
      AND (
        current_setting('app.gym_wide', true)::boolean IS TRUE   -- Gym Owner
        OR location_id = ANY(string_to_array(
             current_setting('app.location_ids', true), ',')::uuid[])
      )
    )
  );

Context must be set with SET LOCAL, inside the transaction

Plain SET would be a cross-tenant data leak. Connections are pooled and reused. SET persists on the connection after the request finishes, so the next request — potentially serving a different gym — would inherit the previous tenant's context. SET LOCAL is scoped to the transaction and is discarded on commit or rollback, which is what makes pooling safe. This is not a style preference; it is the difference between isolation and a breach. 
@Component
public class RlsContextInterceptor {

  @Transactional  // SET LOCAL requires an open transaction to be meaningful
  public void apply(AuthContext ctx) {
    jdbc.update("SET LOCAL app.gym_id = ?",         ctx.gymId());
    jdbc.update("SET LOCAL app.location_ids = ?",   String.join(",", ctx.locationIds()));
    jdbc.update("SET LOCAL app.gym_wide = ?",       ctx.isGymOwner());
    jdbc.update("SET LOCAL app.is_super_admin = ?", ctx.isSuperAdmin());
  }
}

A @Transactional aspect applies this at the start of every request-bound transaction. A request that somehow reaches the database without context set resolves current_setting(…, true) to NULL, the policy matches nothing, and queries return zero rows — the safe failure direction, and a loud one in testing.

Super Admin access is deliberate and audited

app.is_super_admin bypasses the policy, which FR-ORG-09 requires for cross-gym oversight. It is set only when a Super Admin acts in an explicitly cross-gym context, never as an ambient default, and every such request is written to the audit trail. Note that this bypass grants operational visibility only, and never exceeds a Gym Owner's data tier. Purpose restrictions on health data are enforced separately at the application layer, since they are restrictions on purpose rather than on tenancy — see LB-ENG-1.0 §13 for the authoritative permission matrix.

Testing

RLS cannot be verified against an in-memory database; it requires real Postgres. Testcontainers spins one up per suite. The standing test attempts, through every repository, to read another location's members, another gym's payments, and a sibling location's attendance — asserting empty results in each case. This suite is the evidence for NFR-SEC-01a and NFR-SEC-01b, and is the last thing that should ever be disabled to make a build pass.

5.4 Migrations

Flyway, versioned SQL, applied by lb_migrator at deploy time before the application starts accepting traffic. Every migration is forward-only; corrections are new migrations. Seed data — the exercise catalogue, muscle group taxonomy, default notification templates — ships as repeatable migrations so environments are reproducible rather than hand-assembled.

6.2 Authorisation — role grants evaluated per location

FR-AUTH-28 requires that effective authority be the union of an account's grants evaluated per location, never the maximum applied everywhere. A trainer who is also Location Admin at one site must not exercise admin authority at another. This is the model's subtlest rule and the easiest to get wrong, so it is expressed once, centrally:

public boolean can(AuthContext ctx, Permission p, LocationId at) {
    return ctx.grants().stream()
        .filter(g -> g.appliesAt(at))          // scope check FIRST — never skipped
        .anyMatch(g -> g.role().permits(p));
}

Authorisation is evaluated at the service layer, not in controllers, so no endpoint can bypass it by omission. RLS then provides the second, independent line: even a service method with a flawed check cannot return rows the database will not release. The two controls are deliberately redundant — a single mistake breaches neither.

7.2 Offline Sync

1. Local writeOperation written to the SQLite outbox with a generated UUID key. UI confirms instantly.
→
2. TriggerSync attempts on app foreground, on connectivity restored, and on a periodic background task.
→
3. SubmitQueued operations posted in order, each carrying its idempotency key and original timestamp.
→
4. SettleServer deduplicates on the key. Success clears the row; permanent failure surfaces to the user.

Only check-in and workout set logging are queued. The reason is structural rather than a matter of effort: as noted in ADR-06, both are non-contending — a check-in is an append-only fact, and a workout log has exactly one author. Neither requires arbitration, so no conflict-resolution strategy is needed. Bookings, payments and plan changes contend for shared resources and are therefore always online, arbitrated by the database.

7.3 Idempotency — what makes the queue safe

The retry problem is that a network failure is ambiguous: the client cannot tell a request that never arrived from one that succeeded but whose response was lost. Retrying risks duplication; not retrying risks loss.

Idempotency keys resolve it. The client generates a UUID per logical operation and reuses it across every retry. The server stores it against the resulting record under a unique constraint, so a replay returns the original outcome rather than creating a second. This is what lets the client retry freely, and it is simultaneously how FR-ATT-05's duplicate-rejection requirement is met under offline replay — one mechanism satisfying a correctness requirement and an availability requirement at once.

7.4 Push Notifications

An Expo push token is registered per device on sign-in and invalidated on sign-out. Dispatch runs through the job queue (ADR-09), so a slow or failing push provider never blocks a request. Delivery receipts are polled from Expo and recorded per notification, satisfying FR-NTF-06. Quiet hours (FR-NTF-04) and de-duplication (FR-NTF-07) are applied server-side at dispatch, never on the device — the device cannot be trusted to suppress what it has already received.

8. Background Processing

12. Performance and Scaling Strategy

The SRS targets — 50 gyms, 200 locations, 100,000 members, 500 concurrent users, 5 million attendance rows — are modest for this stack. A single well-sized instance and a single Postgres database handle them with room to spare. The interesting characteristic is not volume but shape: load concentrates violently into the 6–8am and 6–9pm windows (NFR-SCL-04), so capacity must be sized against peak and not average.

PressureResponse, in order
Check-in burstsJava 21 virtual threads absorb concurrent blocking calls without reactive rewriting. Derived work (streaks, notifications) is already off the request path via the job queue.
Slow dashboardsIndexes first; then materialised views refreshed by job for the heaviest reports; then the async escape NFR-PRF-06 already permits.
Database contentionConnection pool tuning; read replicas for reporting once write and read patterns genuinely diverge. Not before.
Instance saturationVertical scaling first (a one-line change). Then ALB plus a second instance — the application is stateless and the queue already tolerates concurrent consumers, so nothing else changes.
Storage growthCloudinary credits are the binding constraint on media, not disk. Cap upload dimensions at the point of upload and rely on derived renditions rather than storing multiple sizes. Monthly partitioning of attendance if row volume ever demands it.
Measure before optimising. Every scaling move above is a response to an observed metric, not a precaution. The metrics in §11 exist to make that possible. The architecture's most valuable performance property is that none of these responses requires re-architecting — each is a configuration or infrastructure change against the same codebase.

ARK-08PgBouncer transaction mode breaks prepared statementsNeon's pooled endpoint requires prepareThreshold=0 on the JDBC URL. Symptom is intermittent, confusing errors under load rather than a clean failure — worth configuring correctly at the outset.
ARK-09Progress photographs uploaded to Cloudinary's public delivery typeThe default upload type yields a permanent public URL. One sensitive image uploaded through the default path is a privacy breach that cannot be undone by deleting the record, because the URL may already be cached or shared. Mitigated by routing every upload through MediaService with sensitivity as a required argument rather than an option, and by a test asserting that no sensitive asset is ever created with the public type. Verify plan support for expiring authenticated delivery before Phase 2 (ADR-15).
ARK-10Media has no second copyCloudinary holds the only copy of every uploaded asset. Unlike the database, there is no nightly dump. Accepted during development; before a pilot, add a periodic export of sensitive media to the same S3 backup bucket used for database dumps.

What this document does not decide. API endpoint signatures, full table definitions, screen designs and test plans belong to implementation, not architecture. Everything else is deliberately left to be decided with more information than we have today.
